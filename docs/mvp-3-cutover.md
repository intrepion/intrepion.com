# MVP 3 first-upgrade procedure

Status: **approved production cutover complete, including owner verification, protected recovery and normal hourly-retention verification**. See [live evidence](research/mvp-3-launch-live.json). This document is an operator runbook, not an automated deployment. Do not dispatch the ordinary Deploy workflow for the first upgrade: its compatibility guard intentionally refuses the MVP 2 schema.

## Preparation record before execution

- `web/maintenance/` preserves the maintenance page used for MVP 2 and its no-store/security headers. It has not been published for this upgrade.
- `node scripts/prepare-mvp3-credentials.mjs` creates or validates two distinct random 32-byte hex secrets in the ignored `.env.setup.mvp3-credentials.json`, mode 0600. It never installs or rotates provider secrets. Do not print, commit or place this file in a client build. An invalid existing file fails rather than being overwritten.
- A private environment payload is staged at `.env.setup.mvp3-render-env.json`, mode 0600, with both credentials and `CUSTOMER_WRITES_FROZEN=true`. It preserves all directly configured Render variables. Its source fingerprint is in the adjacent private manifest; **recapture and compare the entire source environment immediately before installation** so staging cannot overwrite intervening changes. Linked environment groups remain separately managed. No provider environment has been changed.
- Read-only Render inspection found Free, one instance, auto-deploy off, and the existing MVP 2 deployment live. The shutdown delay was not returned, so the conservative drain calculation below uses the documented maximum. Recheck these facts at execution.
- [Hosted evidence](research/mvp-3-hosted-rehearsal.json) includes a production build booted frozen against a restored schema-6 database, rejected writes before migration, migrations through 0014 while frozen, private policy bootstrap, saved reads and reopening/retry. Both temporary databases were removed. These are isolated checks, not a production write boundary or fresh Google sign-in.

## Freeze semantics

`CUSTOMER_WRITES_FROZEN` accepts exactly `true` or `false`; omission defaults to false and any other value rejects startup. It is read once at process startup. `/auth/config` reports `customer_writes_frozen`; `schema_version: 3` identifies the API contract and **does not prove that database migrations have run**.

When true, middleware blocks customer mutation RPCs, all sign-in/challenge/logout POSTs, scheduled household erasure and unknown routes with HTTP 503 / Connect `unavailable` and `Retry-After: 60`. Saved-read RPCs, GET session/config/liveness and CORS preflight remain available. The private operator service remains available with its distinct bearer credential so policy can be configured during maintenance; customer sessions and the maintenance credential cannot authorize it. Do not run any other operator or direct database writer during the snapshot boundary.

The flag does not drain a previous process, freeze other services or cancel database work already submitted. Liveness remains green during maintenance. Before migrations, schema-dependent reads can fail; the maintenance page keeps new visitors outside the app.

## Execution sequence after launch approval

1. Pin the **full SHA on main with passing CI**, including its production container build. Build the static client for `https://api.intrepion.com` from that exact checkout. Record the current live SHA, Pages deployment, database ID and backup marker privately. Verify auto-deploy off, one instance, no other customer/database writers, household automation still disabled and no concurrent deployment/migration/retention job. Keep normal encrypted backups and the watchdog enabled; coordinate around an in-progress export. Do not broaden credentials or change plans.
2. Publish `web/maintenance/` to the existing root Pages project, with the pinned SHA as deployment metadata; keep the www redirect. Verify maintenance HTML and headers over HTTPS. This does not freeze the API.
3. Read all pages of Render's current directly configured environment, compare against the staged source fingerprint, and regenerate the complete payload on any difference. Save the preserved list plus both credentials and freeze=true using the **bulk** `PUT /v1/services/{id}/env-vars` endpoint. Verify the complete saved list privately. Do not use single-variable updates or assume a restart incorporates pending configuration. [Provider evidence](research/mvp-3-cutover-provider-facts.md) explains these distinctions.
4. Explicitly deploy the pinned SHA via `POST /v1/services/{id}/deploys` with `{"commitId":"<full SHA>"}`. The database is still schema 6. Poll the returned deployment ID and require `live` and `commit.id` equal to the pinned SHA. Verify `/health/live`, config freeze=true, auth challenge POST503 and each customer mutation/retention route503 directly, including a request with the valid maintenance credential. Never log cookies or bearer values. Use rejected empty bodies so a failed freeze check cannot create content.
5. **Drain the old writer before backup or DDL.** After observing the frozen deployment live, wait at least 60 seconds plus the configured shutdown delay, followed by at least 30 seconds for outstanding D1 work. Because inspection did not expose a configured delay, use the documented 300-second maximum: **390 seconds minimum**. Verify the old instance is gone through provider lifecycle evidence. Check retained-content/history and session/challenge fingerprints twice across the final drain interval; instability means stop and investigate, not migrate. This conservative wait and stability check are operational evidence, not a provider guarantee of remote-request cancellation.
6. With freeze still verified and no operator/direct writers, dispatch **Daily encrypted backup** normally (no failure-test input). Require success and a new verified marker created after the drain boundary. Download with the backup reader, verify ciphertext hash/length, decrypt privately, integrity-check and compare the exported retained content/history with the frozen source. Remove private plaintext afterward. Require a fresh complete prefix-scoped erasure ledger and an isolated protected restore. The earlier rehearsal backup does not replace this final backup.
7. Only after that evidence passes, use the migration credential with the reviewed production configuration:

   ```sh
   node scripts/cloud-config.mjs
   ./node_modules/.bin/wrangler d1 migrations apply DB --remote --config server/wrangler.production.json
   ```

   Supply `CLOUDFLARE_API_TOKEN` from the private migration credential without echoing it; the configuration must name the recorded production database. Confirm precisely 0007–0014 are pending before answering the migration prompt. The frozen MVP 3 process stays running. Require all 14 records, foreign-key integrity, unchanged retained-content/history fields, correct legacy actor backfill and writer fences. Clear old sessions/challenges at this approved boundary, preserving content. Reverify blocked mutations.

8. Through the private operator API, read the existing owner's exact Google subject and revision; preview the plan in `mvp-3-pilot-policy.json`, require allowed/no exceeded spaces, apply with the returned preview token and read every value back. Set and read back 100 items / 20 sections with the expected structural revision. Record receipts privately. Do not enable another account. Run `scripts/deploy-preflight.mjs` read-only with the migration credential and require a pass.
9. Publish the matching built static client while the API stays frozen. Recheck saved reads using an existing approved session if available; clearing sessions requires fresh auth after reopening. Keep ordinary auth/retention writes blocked until policy, schema and client checks pass.
10. Preserve all current Render variables again, changing **only freeze=false**, using bulk save-only and readback. Explicitly redeploy the **same pinned SHA**. Verify exact revision and config freeze=false. The old frozen instance is safe during the rolling handoff. Verify fresh owner Google sign-in and retained real data, a confirmed synthetic task/reload/edit/retry and cleanup, headers/root/www, and the approved household workflows. No public signup or dependent/PIN access.
11. Read back a new current-schema encrypted backup and rehearse protected recovery in isolation. Install the separate maintenance credential in the operations environment privately, verify maintenance authentication and failure notification, and enable `HOUSEHOLD_OPERATIONS_ENABLED` **only with explicit authorization**. Before declaring launch complete, resolve the separate size/headroom monitoring gate in `mvp-3-release.md`; additional account admission still requires daily account-wide D1 review. Record exact revisions, run IDs, timestamps and accepted limitations.

## Failure and recovery

Before step 7, aborting can preserve schema 6 and deliberately redeploy the recorded compatible MVP 2 revision with the original saved environment; verify it before removing maintenance. Do not casually resume a suspended service or assume its revision/configuration.

After any migration begins, keep maintenance and customer freeze enabled. Diagnose and fix forward using a reviewed compatible MVP 3 revision. Never run an MVP 2 writer against budget-aware schema or remove writer fences to force rollback. Partial migration or bootstrap must pass integrity and the deployment guard before reopening. If restoration is required, restore the frozen encrypted backup **into a separate destination**, replay the fresh complete independent ledger, upgrade to current schema, clear auth state and verify policy/content/integrity before a separately reviewed destination switch. Preserve the original destination for diagnosis. Do not overwrite production or bypass erasure protection to recover availability.
