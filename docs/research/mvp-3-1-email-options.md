Cloudflare Email Service's free destinations require advance account verification. Arbitrary-recipient sending requires Workers Paid, so it does not meet the same $0 invitation-email goal: [Email Service pricing](https://developers.cloudflare.com/email-service/platform/pricing/), [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/).

Resend is proposed, not selected. Its documented quotas fit an initial invitation workload; this is a product inference, not a volume forecast or permanent price guarantee. [Terms](https://resend.com/legal/terms-of-service) can change and do not promise an irrevocable free tier. Keep explicit application send bounds and require approval for paid services.

Use a dedicated sending subdomain and the exact provider-generated authentication records. Preserve existing mailbox routing and root MX. Resend documents [domain setup](https://resend.com/docs/dashboard/domains/introduction) and [avoiding existing MX conflicts](https://resend.com/docs/knowledge-base/how-do-i-avoid-conflicting-with-my-mx-records); do not hard-code a stale MX/TXT recipe.

Google is not authoritative for the current ownership of every third-party Google-account email address. A private token freshly delivered only to the invited mailbox can provide a separate possession challenge. To rely on this, the token must not be exposed to the inviting head/admin as a copyable link, must be hashed at rest, and must not be consumed by email-scanner GET requests. This is design reasoning based on [Google's verification guidance](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token); it is not a provider guarantee. Keep stable account identity keyed by Google's `sub`.

AWS now defaults new account/region combinations to Essentials at $0.16/1,000 rather than à-la-carte. Explicitly select à-la-carte if choosing its lower base rate. Source: [AWS plan launch](https://aws.amazon.com/blogs/messaging-and-targeting/introducing-amazon-simple-email-service-ses-pricing-plans/) and [plan management](https://docs.aws.amazon.com/ses/latest/dg/pricing-plans.html). Introductory AWS credits and earlier first-year SES allowances do not count toward ongoing affordability.

SES sandbox is restricted to verified recipients; [production access](https://docs.aws.amazon.com/ses/latest/dg/request-production-access.html) is needed for ordinary invitation recipients. AWS Budgets provides delayed monitoring/actions, not an absolute monthly spending cap: [budget guidance](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html). Application send ceilings remain necessary. No move to EC2 is required to call SES from the existing server; this is an architectural inference from its API.

Recommendation: Resend Free remains a reasonable $0 initial choice if 100/day and 3,000/month fit, but it is not uniquely cheapest. Brevo has more free daily headroom when branding is acceptable; SES à-la-carte is a strong low-cost growth choice before paying a $15–$20 monthly email subscription. A permanently free allowance is cheaper than paid SES while the workload fits. No provider is selected by this analysis.

Mailbox SMTP and self-hosting are also possible categories. They would require a separate feasibility assessment of credentials, provider automation rules, sending restrictions, host/network costs, reputation and bounce handling. They are not assumed to be free, reliable substitutes for a transactional service. None is proposed for implementation here.

## SES implementation facts for remaining decisions

- SES SendEmail v2 has no native idempotency/client-token parameter. AWS documents acceptance despite a caller-visible error and possible duplicate email on retry. Use durable application jobs and stable message tags, while explicitly avoiding an exactly-once delivery guarantee: [API](https://docs.aws.amazon.com/ses/latest/APIReference-V2/API_SendEmail.html), [sending process](https://docs.aws.amazon.com/ses/latest/dg/send-email-concepts-process.html).
- Configuration sets can publish delivery/bounce/complaint events to SNS or EventBridge. SNS HTTPS consumers must validate signatures and expected topics, including subscription confirmations. Persist/deduplicate before acknowledging. A dead-letter queue avoids silently losing exhausted retries: [event destinations](https://docs.aws.amazon.com/ses/latest/dg/event-publishing-add-event-destination.html), [SNS verification](https://docs.aws.amazon.com/sns/latest/dg/sns-verify-signature-of-message.html), [retry policy](https://docs.aws.amazon.com/sns/latest/dg/sns-message-delivery-retries.html).
- Account suppression is regional. Hard-bounce and complaint suppression should be verified; Gmail does not provide SES complaint feedback. Suppression is not proof that all unwanted invitations are detected: [suppression documentation](https://docs.aws.amazon.com/ses/latest/dg/sending-email-suppression-list.html).
- Easy DKIM and an optional dedicated MAIL FROM subdomain can coexist with existing root inbox MX. Oregon/us-west-2 supports API sending and is a proposed single-region fit for Render Oregon: [identities](https://docs.aws.amazon.com/ses/latest/dg/creating-identities.html), [MAIL FROM](https://docs.aws.amazon.com/ses/latest/dg/mail-from.html), [endpoints](https://docs.aws.amazon.com/general/latest/gr/ses.html).

These facts guide the interview; no AWS account, region, DNS or billing setting has been changed. Detailed outbox, feedback queue and credential design follows product scope confirmation.
