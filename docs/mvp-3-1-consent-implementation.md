# Consent invitation implementation checkpoints

The owner approved the scope and prototype. The fixed review baseline is commit `b620709`, which records the approved design; the throwaway prototype is on `prototype/consent-invitations`. Existing unrelated untracked prototypes are not part of this feature.

The approved test boundaries are generated ConnectRPC client through local D1, browser through the real local API, encrypted backup and recovery, and signed provider feedback through the local API. The latter three use local emulators where applicable, and browser end-to-end checks remain local.

Integration points identified before implementation:

- The existing `EmailInvitationService.ChangeInvitation` creates an invitation directly from a supplied email. Replace this initiation with an explicit, verified request and head decision; preserve safe handling of existing invitations during migration.
- `auth/onboarding.rs` currently establishes an onboarding session from an emailed invitation, checking the email address. Requesters need a separate limited Google-verified session without creating an account, and the eventual invitation must bind both the verified Google subject and address.
- `mail.rs` currently claims and counts invitation attempts in an atomic D1 batch against the shared 10,000-attempt monthly ceiling. Approval and notifications must coordinate with that accounting, including concurrent approvals, retries, suppression, and recovery holds.
- Recovery currently revokes pending invitations and pauses growth. The new links, request records, notification settings and queues must be incorporated, including retention cleanup before activating a recovered database.
- Head departure, suspension, household closure, retention and storage accounting already have separate paths. Every new record and transition needs to participate in those paths and in the approved race and privacy rules.

Implement in vertical slices through the agreed boundaries, then perform the fixed-baseline specification and standards reviews.

On 2026-10-28, SES in Oregon reported a verified `notify.intrepion.com` identity, but production sending was disabled and there were no SES configuration sets or SNS topics. AWS lists à-la-carte outbound email at $0.10 per 1,000 messages, so the application's 10,000-attempt monthly ceiling corresponds to up to $1 in base send charges, plus applicable message data, feedback delivery, queue, monitoring, and other usage charges; this application ceiling is not an AWS billing cap. SNS and SQS are usage-priced. This estimate does not assume a trial or introductory credits. Verify actual regional pricing and account usage when provisioning. Sources: [SES pricing](https://aws.amazon.com/ses/pricing/), [SNS pricing](https://aws.amazon.com/sns/pricing/), [SQS pricing](https://aws.amazon.com/sqs/pricing/).

AWS's [SNS dead-letter documentation](https://docs.aws.amazon.com/sns/latest/dg/sns-dead-letter-queues.html) says an encrypted SQS dead-letter queue requires a customer-managed KMS key with appropriate SNS access. [KMS pricing](https://aws.amazon.com/kms/pricing/) lists a recurring charge for a customer-managed key in addition to request charges. The owner is choosing whether to accept that fixed cost for encryption of potentially identifying feedback; do not silently provision the key or use an unencrypted queue before that choice.

The intended setup is a dedicated SES configuration set and SNS topic in Oregon, signature version 2, an HTTPS subscription to the deployed feedback endpoint with bounded retries, and a dedicated SQS dead-letter queue with a 14-day retention period. The SNS topic policy must restrict SES publishing to this account and the intended source. AWS's [queue-policy example](https://docs.aws.amazon.com/sns/latest/dg/sns-configure-dead-letter-queue.html) scopes SNS access by topic ARN; use a dedicated topic and queue for the single application subscription, and verify the actual service grant rather than assuming a subscription ARN works as `aws:SourceArn`. Configure queue-depth monitoring and a controlled, authenticated replay procedure before enabling delivery. Grant the application only SES send access to the intended identity and configuration set; monitoring and provisioning credentials must remain separate. HTTPS subscription confirmation must wait until the matching API and feedback configuration are deployed. These are preparation notes, not evidence that any of the resources have been created or verified.

The owner chose KMS encryption. In Oregon, the dedicated SES configuration set `intrepion-invitations` was created with its sending option disabled, an encrypted signature-v2 SNS topic and encrypted 14-day SQS dead-letter queue were created with a dedicated customer-managed KMS key, and the SES event destination was attached to that topic. The queue policy permits delivery only from the dedicated topic; the topic permits SES publishing from this account's configuration set. AWS accepted these settings and the event types, queue key and retention were read back. The HTTPS subscription, dead-letter delivery, monitoring, and application credentials have not yet been configured or tested. The account remains in the SES sandbox and no invitation sending is enabled. The customer-managed KMS key incurs its recurring charge even while sending is disabled.

The GitHub queue monitor subsequently passed its read-only manual run; its dedicated IAM credential has only `sqs:GetQueueAttributes` for the feedback queue. A separate sender identity is scoped to SES `SendEmail`, the notification domain, the intended configuration set and `no-reply@notify.intrepion.com`; its staged credential was verified without revealing it. The notification domain defaults to the disabled configuration set. The encrypted invitation signing key was copied to the owner's recovery USB, compared with the staged archive and successfully decrypted with the recovery key on that drive.

The test checked the event against the simulator message ID and removed only that message, then removed its temporary subscription and disabled configuration-set sending. Readback confirmed sending disabled and no remaining subscriptions. This does not test the production HTTPS endpoint, signed feedback intake, failed-delivery dead-letter routing or replay.
