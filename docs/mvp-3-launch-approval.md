## Proposed scope

1. Run the household-retention workflow once with `test_failure: true`, while scheduled retention remains disabled. This intentionally fails only its notification step, sends the configured GitHub failure notification and makes no API request or erasure. Confirm the owner's receipt before starting maintenance.
2. Publish the existing maintenance page at `intrepion.com`. Preserve the www redirect, DNS, provider plans, spending controls and existing twice-daily backups/hourly watchdog. Deploy the approved API revision with customer/auth/retention writes frozen. Install the two separately staged private server tokens through the preserved full Render environment; no credential enters the web build.
3. Verify exact API revision and actual rejected writes. Drain the old writer using the conservative **390-second minimum after the frozen revision is live**, plus evidence of stable retained data/auth-state fingerprints. This wait is only part of the interruption: builds, backup, migration and checks add time. Take a new encrypted backup after this real write boundary, verify its readback and protected restore, and stop if any gate fails. Previous rehearsal backups do not substitute for it.
4. Apply only migrations **0007–0014** to the recorded production D1 database. Verify all migration records, foreign keys, preserved content/History and writer fences. Clear existing sessions/challenges. Use revision-checked operator previews to assign the configured owner's approved plan: **250 items, 10 shopping lists, 10 templates, 25 runs, 128 KiB logical retained storage and 2 simultaneous households headed**. Set uniform structural caps of **100 items and 20 sections per collection**. Re-read exact values and require the deployment guard to pass before reopening.
5. Publish the staged matching web client for `https://api.intrepion.com`, then explicitly redeploy the same API SHA with freeze=false. Require a fresh owner Google sign-in, retained real lists and a user-confirmed temporary task/reload/edit check. Prior two-head access/allocation/copy/erasure tests and isolated hosted migration/recovery evidence remain required; no second production identity is admitted as a launch test.
6. Read back a fresh current-schema encrypted backup and verify protected recovery. Put only the maintenance token in the GitHub `operations` environment. Verify rejection of incorrect credentials and acceptance of the correct maintenance credential with an explicitly nonexistent household UUID. **Enable hourly household retention only after** recovery, notification receipt, owner sign-in/persistence and authorization checks pass. A normal workflow invocation must then pass. This conditional activation is part of the requested launch approval; without that approval, leave the variable disabled.

The pilot starts with the current owner only. No public signup, additional-account admission, dependent/PIN access, billing, paid service, plan upgrade, AI feature, DNS/mail change or bulk erasure is included. Account-wide D1 usage must be reviewed manually before admitting another account. Growth/cost and household-backlog reviews remain manual under the [monitoring procedure](mvp-3-monitoring.md).

## Recovery and stopping conditions

Before migrations, the recorded compatible MVP 2 revision/environment and prior Pages deployment provide an abort path after verification. After migrations begin, retain maintenance and the write freeze and fix forward using compatible MVP 3 code. **Do not restart an MVP 2 binary against the new schema or remove writer fences.** If restoration becomes necessary, preserve the original database and prepare protected recovery in a separate destination for a separately reviewed switch; this approval does not authorize overwriting the production database or bypassing ledger protection.

Pause the cutover on an unexpected source revision, environment mismatch, unstable freeze boundary, failed backup/ledger verification, unreviewed migration, failed integrity/policy check or unavailable recovery. Record partial progress privately and preserve retry identities. Numerical plan approval, CI success and this packet's preparation do not themselves authorize launch.

## Owner involvement

The owner must be available to confirm the intentional notification email and, after reopening, a fresh Google login and retained-list/persistence checks. No Google password, token or cookie should be sent in chat. The site remains unavailable during the maintenance phase; there is no fixed completion-time guarantee. The final request asks whether to start this exact action set now.
