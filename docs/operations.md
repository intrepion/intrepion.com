## Backup and recovery

Daily backup runs at 04:17 UTC. It exports D1 privately, restores the SQL into isolated in-memory SQLite for integrity/schema checks, encrypts with age, uploads to B2, downloads and hashes the encrypted archive, then writes and reads back a verification marker. Only after those checks does it prune versions under its exact daily backup paths older than the current UTC day plus six prior days. It never stores plaintext exports as GitHub artifacts. A 20 MiB export ceiling forces a storage-budget review before larger backups are accepted.

The separate watchdog runs hourly at minute 43. It fails when no verified marker exists, the recorded snapshot is older than 24 hours or invalid, provider access fails, or the referenced archive's metadata does not match. The watchdog has no D1 credential and cannot write or prune backups. Configure bucket retention and audit historical versions as an additional precaution, using settings consistent with seven daily backups. Do not apply object lock that prevents the agreed expiration policy.

Daily checks establish that plaintext SQL restores and uploaded ciphertext matches. They do not decrypt on GitHub: the private age key stays offline. Before launch and after backup-process changes, download an archive privately and run:

```sh
umask 077
age -d -i /private/path/recovery.age-key -o /private/path/restore.sql /private/path/database.sql.age
node scripts/backups.mjs verify-sql /private/path/restore.sql
```

Restore into a new isolated local or D1 database, delete restored sessions and login challenges, and verify task operations before changing the running service's database ID. Deleting sessions prevents recovery from reviving old sessions. Keep credentials and plaintext out of logs and version control; remove temporary exports after the drill. Do not overwrite the live database without an explicit recovery decision.

The recovery objectives remain 24-hour data loss and restoration within one day, as best-effort targets. Native GitHub emails only report jobs that actually execute. Shared scheduler delays, disabled schedules, or a GitHub outage can prevent both jobs and their alerts; this is the accepted MVP blind spot. No Sentry or external heartbeat monitor is included.

3. Suspend the Render API to prevent writes during the transfer. Keep it suspended if any subsequent operation fails. Save the exact passing deployment revision and previous owner setting privately.
4. Use authenticated, parameter-bound D1 queries to change `tasks.owner_sub` from the verified old subject to the verified new subject. Transfer `retired_task_ids.owner_sub` in the same direction so deleted task IDs remain retired. Check affected-row counts against the recorded counts. Do not delete/reinsert task rows: deletion creates retirement receipts.
5. Delete all `sessions` and `login_challenges` rows so no previous session or outstanding challenge remains usable. Update Render's `GOOGLE_OWNER_SUB` to the verified replacement subject, then deploy an exact passing revision and resume the service. Do not change the OAuth client ID, web origin or database ID as part of this operation.
6. With the replacement Google account, sign in and verify the previous tasks and their confirmed fields, including edit/complete/reopen/delete behavior. Verify that the former account is rejected and old session cookies no longer work. Then take another encrypted backup and update the private recovery record.

If transfer verification fails, suspend the API again. Before allowing new writes, reverse both subject updates using bound parameters, restore the previous owner setting, delete all sessions/challenges again, and redeploy the recorded passing revision. If new writes occurred or row counts differ, use the isolated backup-recovery process and reconcile those writes before changing the live database. Never overwrite the live database merely to correct an identity setting. Previously downloaded backups remain encrypted under the existing recovery key; rotating that key is a separate operation.

## Security and retry corrections

Deletion now requires the last observed task revision. A stale or legacy client must reload and review the current task before deleting it. Repeated deletion at the same revision succeeds once the task is absent. The additive `0002_retired_task_ids.sql` migration records only the owner subject and deleted task ID in a separate table, using a deletion trigger so retirement is atomic with deletion. Create retries cannot reuse retired IDs; titles and notes are removed from the live database. Receipts are retained to prevent arbitrarily delayed retries, are included in full database backups, and are transferred with the owner identity. Receipts begin at this migration; historical deleted IDs cannot be reconstructed automatically.

The API limits sign-in challenges and login attempts to 30 per caller per minute, with a separate 600-per-minute process safeguard. Rejected requests from an already-limited caller do not spend other callers' allowance. The caller map is bounded and cleared each minute; addresses are never logged. Direct/local deployments use the socket peer and ignore forwarded headers. Only a production process with Render's reserved `RENDER=true` environment trusts the first `X-Forwarded-For` address supplied by its public edge; a missing or malformed trusted address fails closed. Do not set `RENDER=true` on a directly exposed server. This protects the reviewed single-caller lockout; a distributed flood can still reach the global safeguard or hosting quotas. See [Render's client-IP guidance](https://render.com/articles/how-render-handles-ddos-attacks).

The readiness probe requires HTTP 200 and the exact application `ok` body, and retries loading pages or transient failures within its overall 90-second deadline. Timing includes reading that body. It remains a process check, not proof of database availability.

JWT verification uses the AWS-LC backend instead of the RustCrypto RSA backend. The application still accepts only RS256 Google tokens with the same claim checks; its public-fixture tests exercise the replacement backend. Node is pinned to 26.12.1; Rust remains pinned to 1.99.1. Local toolchain and regression results are recorded with the change; application deployment must still pass the exact-revision CI gate.

The web build also emits Cloudflare's `_headers` file from a normal Astro endpoint and renames it after generation. An underscore-prefixed Astro source route had previously been ignored, so the intended CSP/frame restrictions were absent from the static output. Both CI and deployment now require the emitted file. Verify the actual HTTPS response headers and Google sign-in button after deployment; local Astro development does not emulate Pages header processing.

Regression evidence for these corrections: the original caller-lockout test failed with HTTP 429 for the second caller; both task race tests initially failed because the requests incorrectly succeeded; the original probe counted a loading page as ready. After correction, six Rust tests, eight real HTTP/local D1 workflows, and the probe tests pass. The replacement dependency graph contains 201 registry crate versions and the OSV query returned zero advisories with no pending pagination. Node 26.12.1 was checksum-verified against the official distribution and used for local validation; no system-wide toolchain was changed. Live rollout still requires passing CI for the exact commit. Refresh older browser tabs after rollout: the API deliberately refuses deletion requests without a revision rather than risk deleting unseen edits.
